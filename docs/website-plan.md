## 정식 오픈(T-2) — ✅ 완료 (2026-08-10)

**parkinon.com 이 콘텐츠 사이트로 정식 전환됐다.** 실제 프로덕션(`parkinon-web` 프로젝트,
`parkinon.com` 연결)에 `merged-dist`를 배포하고, `/`·`/ko/`·`/app/`·`/app/records`·
`/r/:token`→`/app/r/:token`·`/records`→`/app/records`·`/admin`→`/app/admin`·`/terms`·
`/privacy`·`/delete-account`·`/app-ads.txt`·`/about`→`/ko/`·`/lifestyle`(옛 주소) 를
실제 도메인에서 전부 재확인했다. Playwright 로 `/`(콘텐츠 홈)·`/app/`(코드 입력 화면)
둘 다 콘솔 에러 없이 뜨는 것까지 확인함.

앱(`parkinon-app`)의 "PC에서 보기" 안내 문구도 `parkinon.com` → `parkinon.com/app` 으로
고쳐서 OTA 배포 완료(2026-08-10, production 브랜치, Android·iOS 둘 다).

⚠️ **배포 시 주의**: 처음 배포하고 몇십 초 정도는 Cloudflare 전역 엣지에 새 배포가 다
퍼지기 전이라 일부 요청이 옛 응답을 줄 수 있다(실측: 배포 직후 `/records`가 잠깐 200,
15초 뒤부터는 계속 301로 안정). 배포 직후 확인할 땐 캐시 우회 쿼리(`?t=<timestamp>`)를
붙이거나 몇 번 재요청해서 판단할 것 — 한 번 요청으로 "안 된다"고 단정하지 말 것.

⚠️⚠️ **실제로 사고가 났었다(2026-08-10, 몇 시간 뒤 발견)**: 첫 정식 오픈 배포를
`PUBLIC_SITE_URL` 없이 했다. `site/astro.config.mjs`는 이 env가 없으면 기본값
(`parkinon-site-dev.pages.dev`)으로 빌드하는데, 그 결과 `Astro.site.host`가
`parkinon.com`이 아니게 되어 **robots.txt가 "Disallow: /"로, meta robots가
`noindex`로, sitemap 주소가 dev 도메인으로** 나갔다 — 실제로는 parkinon.com에 떠 있는데
검색엔진은 아예 색인을 못 하는 상태로 몇 시간 있었다. `scripts/merge-deploy.mjs`가
Astro 빌드 시 `PUBLIC_SITE_URL=https://parkinon.com`을 명시적으로 넘기도록 고쳐서
재배포했다. **교훈**: 정식 배포 후에는 매번 `curl`로 실제 도메인의 robots.txt·
sitemap-index.xml·`<meta name="robots">` 세 가지를 직접 확인할 것 — 빌드 로그가
깨끗해도 env 변수 하나가 빠지면 조용히 틀리게 나간다.

또한 `/app/`(로그인용 6자리 코드 화면)은 검색에 잡힐 콘텐츠가 없어 robots.txt에
`Disallow: /app/`을 추가했다.

⚠️ **애드센스 신청 준비하며 하나 더 발견(2026-08-10)**: `/ko/tools`(복약 시간표 도구)가
헤더·푸터엔 안 걸려 있는데(nav.ts에서 일부러 뺌, "열지 말지 추후 결정") **사이트맵에는
그대로 들어가 있었다** — 오너가 공개 여부를 안 정한 페이지가 조용히 검색 대상이 되고
있었다. `astro.config.mjs` sitemap filter와 robots.txt 양쪽에서 `/tools`를 뺐다.

⚠️ **Google Search Console 사이트맵 오류 — 해결됨(2026-08-10)**: `/ko/` URL 접두어
속성으로만 등록돼 있던 상태에서, 오너가 사이트맵 오류("Sitemap이 HTML입니다")를 직접
발견해 재점검을 요청했다. 원인: `/ko/` 속성에 제출한 사이트맵은 자동으로
`https://parkinon.com/ko/sitemap-index.xml`을 가리키는데, 실제 파일은 루트
(`https://parkinon.com/sitemap-index.xml`)에 있어서 그 경로가 사이트 전체 fallback
페이지(HTML)로 응답됐다. **해결**: Cloudflare API 토큰(오너가 DNS Edit 권한만으로 발급,
1일 TTL)으로 `parkinon.com` 존에 `google-site-verification=lPNo9z49Q1kcJSg7R8GJNCPrx_b3qbvU-5r47uggVTQ`
TXT 레코드를 추가 → Search Console에서 도메인(`sc-domain:parkinon.com`) 속성이 즉시
자동 인증됨 → 루트 사이트맵을 그 속성에 새로 제출("성공" 확인) → 예전 `/ko/` 속성의
오류난 사이트맵 항목은 삭제. `/ko/` URL 접두어 속성은 그대로 남겨둠(도메인 속성이
상위 개념이라 중복돼도 무해). 앞으로 `/en/` 등 언어가 늘어도 이 도메인 속성이 전부
커버한다.

### (아래는 오픈 전 작업 기록)

**콘텐츠·SEO 준비는 끝났다.** 진짜 막힌 것은 인프라였다 — `parkinon.com`은 이미 살아 있는
Cloudflare Pages 프로젝트(`parkinon-web`)이고, 기존 앱(SPA, 이 저장소 루트: 6자리 코드
입력·기록보기·관리자·`/api/*`)이 지금 그 자리(`/`)에서 서비스 중이다. "콘텐츠가 루트,
앱은 `/app/`로"(위 구조도)를 실제로 만드는 코드가 없었다 — 이제 만들었다.

- `vite.config.ts` `base:'/app/'`, `App.tsx` `basename="/app"` 로 앱을 `/app/` 서브패스로 이전
- `scripts/merge-deploy.mjs` — SPA 빌드 + Astro 빌드를 하나의 배포 산출물(`merged-dist/`)로
  합친다. `/terms` `/privacy` `/delete-account` `/app-ads.txt` 는 스토어·AdMob 등록 주소라
  **루트 그대로 유지**하고, `functions/`(API)는 그대로 저장소 루트에 둔다.
  ⚠️ **Cloudflare `_redirects` 함정**: `/app/*` 의 리다이렉트 목적지가 `/app/` 아래
  어디에 있든(파일명·깊이를 바꿔도) "무한 루프"로 오판돼 규칙이 무시된다
  (`cloudflare/workers-sdk#11824`). 목적지를 `/app/` **밖**(`/_app-fallback/index.html`)에
  둬야 진짜로 동작한다 — 실제 프로덕션 배포(`wrangler pages deploy`)로 확인함.
- **검증 완료(2026-08-10)**: `parkinon-site-dev` 프로젝트에 `merged-dist`를 실제로 배포해
  `/`·`/app/`·`/app/records`(클라이언트 라우팅)·`/r/:token`·`/records`·`/admin`(옛 주소
  호환 리다이렉트)·`/terms`·`/app-ads.txt` 전부 실제 엣지에서 정상 확인. Playwright 로
  `/app/`에 실제로 접속해 콘솔 에러 없이 코드 입력 화면이 뜨는 것까지 확인함.
- ⬜ **남은 것**: 앱(다른 저장소 `parkinon-app`)의 "PC에서 보기" 안내가 `parkinon.com`을
  가리키고 있다면 `parkinon.com/app`으로 바꿔야 한다 — 이 세션은 그 저장소를 열지 않아서
  확인 못 함. 그리고 실제 프로덕션(`parkinon-web` 프로젝트, `parkinon.com` 연결)에
  `merged-dist`를 올리는 마지막 단계는 오너 최종 확인 후 실행한다(상시 배포 재승인 규칙).
- 정식 오픈(루트 도메인 전환)은 **콘텐츠가 쌓인 뒤**로 미뤘다(오너 결정)

### 메뉴별 상세

**1. 소식** — 전 세계 소재를 골라 묶고 해설을 붙인 소식지. **1벌 쓰고 전 언어로 번역 배포한다.**
한국 독자는 미국 승인 소식을, 프랑스 독자는 일본 동향을 본다. 국내 사이트가 못 하는 자리이고,
번역 1벌로 전 언어가 커버되니 비용 대비 효율이 가장 좋다.

⚠️ **소재를 어디서 어떻게 가져오는가는 `site/docs/news-sourcing.md` 가 정본이다**
(오너 지시 2026-08-13: *"크롤링 방식도 firecrawl이면.. 막힐 경우 대비해서 다른 방식도 넣자.
이걸 규칙에 담아서"*). 요지는 **firecrawl 없이도 돈다**는 것이다 — 주력 소재 두 곳
(Parkinson's News Today · MedicalXpress)이 전부 RSS 로 들어오고, 1차 출처인 PubMed 와
ClinicalTrials.gov 는 공식 API 다. 넷 다 봇 차단도 사용량 한도도 없다.
경로가 살아 있는지는 `npm run check-news-sources --prefix site` 로 확인한다.

발행 주기 근거(2026-08-07 실측):

- **Parkinson's News Today** (파킨슨 전문 매체, 유급 기자) — 최근 50일 **하루 1.2건, 평일만, 주말 0건**
- **MedicalXpress** 파킨슨 분야 — **하루 1.4건**

→ 전 세계 파킨슨 소식의 **총 발생량이 평일 하루 1~3건**이다. 전업 매체도 그 이상 못 낸다.
매일 내면 1호에 1건짜리 단신이 되어 "묶음 소식지"가 성립하지 않고, 언어 수만큼 번역하면 월
130여 페이지 검수가 된다. **주 2~3회면 1호에 3~5건이 묶인다**(주 2회든 3회든 이 근거는
똑같이 성립 — 오너 확정 2026-08-08: "주2-3회로 해라"). 요일을 대체로 규칙적으로 두는 이유는
구글이 발행 **규칙성**을 보기 때문이다 — 빈도보다 끊기지 않는 것이 중요하다.

**2026-08-10 갱신**: 샘플을 1편 만들어 승인받은 뒤, 발행 횟수를 **이틀에 1개(주 3~4회)**로
올렸다(오너: "매일 1개씩 혹은 이틀에 1개씩"). 매일은 기각했다 — 위 실측대로 주말은 소재가
0건이고 평일도 하루 1~3건뿐인데, 지금은 1호에 최소 2건을 묶는 방식(아래 "글 형식")이라 매일
묶으면 재료가 곧 마른다. 이틀에 1개는 하루 평균 1건 정도만 있어도 감당되는 속도라 이 실측
공급량 안에서 안전하게 돈다.

**2. 생활 요령** — 정적 콘텐츠다. 한 번 쓰면 바뀌지 않으므로 오픈 전에 다 만든다.

**3. 임상시험** — 두 블록이 들어간다.

- **모집 중 시험 목록** — ClinicalTrials.gov API v2. **기본은 그 언어판 나라(한국어판=한국)의
  시험을 보여주고, 국가를 바꿔 다른 나라 것도 볼 수 있게 한다**(오너 확정 2026-08-08:
  "기본은 한국 임상시험 나오는데 해외꺼도 볼 수 있게 하라고"). 국가 선택 대상은 제도 1급 7개국과
  같다 — 한국·미국·일본·프랑스·독일·이탈리아·호주 (아래 실측).

  ⚠️ **정정 (2026-08-08)** — 처음 실측한 국가별 수치가 전부 틀렸다. 원인 둘.
  1. **"PD" 약어 충돌** — API 의 `query.cond`(조건 검색)가 느슨해서, 암 면역치료 임상시험의
     키워드("PD-1"·"PD-L1" = Programmed cell Death, 면역관문억제제 표적)와 "Parkinson Disease"가
     겹쳐 매칭된다. 모집 중 673건 중 **47건(7%)이 이 오염**이었다 — 직접 각 시험의
     `conditions` 필드를 검사해서 확인함(제목만 봐도 폐암·자궁내막암·유방암 등 무관한 시험).
  2. **국가명 표기** — `query.locn` 은 텍스트 매칭이라 실제 데이터의 값과 정확히 같아야 하는데,
     한국은 데이터에 `Korea, Republic of` 가 아니라 **`South Korea`** 로 들어 있다(실제 위치
     데이터의 `country` 필드 값을 직접 나열해서 확인함).

  → **그래서 API 의 `query.locn` 국가 필터를 신뢰하지 않는다.** `query.cond` 로만 모집 중
  전체를 받아(페이지네이션으로 전량), **우리 코드에서** ① `conditions` 배열에 "parkinson"이
  실제로 들어 있는지, ② `locations[].country` 가 목표 국가와 일치하는지 직접 검사해서 걸러낸다.
  실제 임상시험 페이지 구현은 이 방식을 따를 것 — API 파라미터로 국가를 거르지 말 것.

**5. 제도·지원** — 국가별로 새로 써야 하는 **유일한** 축이다. 그래서 뒤로 뺐다.
경쟁은 비어 있다 — `파킨슨 산정특례` 검색 시 **10년 된 개인 블로그가 2위**였다.
⚠️ 이건 **경쟁 강도**만 본 것이고 **검색량은 확인된 적이 없다**(할 일 0-1 키워드 조사와 연결).

**6. 도구** — 유지하되 **퀄리티를 보고 뺄 수 있다**(오너 2026-08-07).
지금은 `/tools` 리다이렉트만 남아 있다.

### 확장 비용 구조 — 여섯 중 넷이 "1벌 쓰거나 자동"

|---|---|

```
규제기관·환자단체 ───┘        └─→ 소식 (그 주 것을 골라 묶어 해설)
```

### ⚠️ 신설 축도 "의학 정보는 다루지 않는다" 안에 있다

아래 "⛔ 의학 정보는 다루지 않는다"와 충돌하지 않도록 선을 이렇게 긋는다.

- **운동 영상** — 우리가 운동을 처방하지 않는다. **공식 기관 채널만**(재단·국립병원·환자단체)
  소개하고 개인 유튜버는 쓰지 않는다. 형식은 "이런 공식 자료가 있습니다".
- **임상시험 목록** — 사실 항목(질환·단계·기관·모집 상태·연락처)만 정형화하고 원문 링크. 해석 없음.
- **연구 카드** — 무엇을 조사했나 / 대상 인원 / 결과 / 게재지 / 원문 링크.
  "그러니 이렇게 하세요"는 쓰지 않는다.
  **선별 기준: 3상 이상 또는 메타분석, 또는 주요 저널**(Lancet Neurology, Brain,
  Movement Disorders, JAMA Neurology, Neurology). 저널명이 API 에 나오므로 자동 필터가 된다.
  개별 소규모 연구를 대서특필하면 오보가 된다 — 소규모 비타민D RCT 같은 것이 매달 섞여 나온다.
- 세 축 모두 **담당 의사 상담 문구를 고정으로 단다.**

"이용자가 제공한 정보를 그의 요청으로 **저장**"하는 서비스다.
- **웹사이트: 비해당** — 우리 콘텐츠만 게시하고 이용자 정보를 저장하지 않는다.
- **앱: 해석 여지 있음** — 복약·건강 기록, 사진·영상을 이용자 요청으로 저장한다. '온라인 플랫폼'은
  아니지만(공중 전파 없음) hosting 에 해당한다는 해석이 가능하다. **법률 자문이 필요한 영역 —
  단정하지 말 것.**

**EU 청약철회 — 우리 의무가 아니다**
- 애플: EU 이용자에 대해 **Apple Distribution International Ltd 가 merchant of record**,
  14일 철회 접수도 애플이 처리(rightofwithdrawal@apple.com, 아일랜드 코크)
- 구글: **Google Commerce Limited(더블린)가 판매자**, 철회 절차도 구글이 관리.
  디지털 콘텐츠는 즉시 이용에 동의하면 자동 철회권을 포기하는 구조
→ 스토어 결제 구독에서 **청약철회 처리 주체는 스토어**다. 개발자는 콘텐츠 제공자.

### 글 저장 방식과 발행 흐름 (확정, 2026-08-06)

**글 하나 = 마크다운 파일 하나.** Astro 콘텐츠 컬렉션으로 읽는다.

**왜 마크다운인가**: 지금은 글 하나 추가할 때 ① 글 페이지 `.astro` 새로 만들고 ② 허브 목록

추가해야 한다. 하나만 빠뜨려도 링크가 죽는다. 마크다운 + 컬렉션으로 바꾸면 **파일 하나만
